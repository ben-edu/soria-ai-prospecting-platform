# Phase 8 — AI-Assisted Message Workflow

## Purpose

Phase 8 introduces an AI-assisted message generation pipeline to the SORIA AI Prospecting Platform. It enables operators to generate, preview, and manage prospecting message drafts with AI assistance while maintaining full human control over all external communications. The phase implements the provider abstraction, prompt management, audit metadata, diagnostics, safe failure handling, cockpit UX, and human review workflow.

---

## Implemented Phases Summary

### Phase 8A — AI Message Generation Foundation with `mock_ai`

- Created the initial AI draft preview (`GET /opportunities/{id}/ai-draft-preview`) and AI draft generation (`POST /opportunities/{id}/generate-ai-draft`) endpoints on the opportunities router.
- Added the initial `regenerate-ai-draft` endpoint, later hardened in Phase 8D with generate-first/archive-after-success safety.
- Integrated `MockAIProvider` as the deterministic mock provider for French prospecting email generation.
- No external AI API is called at this stage.

### Phase 8B — Provider Abstraction and Prompt Control

- Built the provider abstraction layer in `ai_providers.py` with a registered provider registry, `get_ai_provider()` resolver, and custom exception hierarchy.
- Built `ai_prompt_builder.py` with `build_prompt_context()` that constructs structured prompt contexts from opportunity, company, contact, offers, and academy resources.
- Added `generate_ai_draft()` orchestrator function in `ai_message_generation.py` that ties prompt building, provider resolution, generation, and output validation together.
- Added config-driven defaults (`AI_DRAFT_PROVIDER`, `AI_DRAFT_PROMPT_PROFILE`, `AI_DRAFT_MODEL_NAME`, `AI_DRAFT_PROMPT_VERSION`) in `app.core.config.Settings`.

### Phase 8C — Audit Metadata on MessageDraft

- Added audit metadata fields to the `MessageDraft` model: `generated_by`, `ai_provider`, `model_name`, `prompt_profile`, `prompt_version`, `review_notes`, `approved_at`, `sent_at`.
- AI-generated drafts store `generated_by="ai"` and populate the AI-specific fields.
- Rule-based and manual drafts store `generated_by="rule_based"` or `"manual"` with null AI fields.
- Audit metadata is exposed through the `MessageDraftRead` schema and visible in the frontend `AiAuditCard`.

### Phase 8D — Diagnostics and Safe Failure Handling

- Added `GET /opportunities/ai-diagnostics/provider` read-only diagnostics endpoint that reports configured provider, model, prompt profile/version, available providers, and provider availability.
- Implemented safe failure in `_safe_generate_ai_draft()` wrapper: `UnknownAIProviderError` returns 503, `AIProviderGenerationError` and `InvalidAIProviderOutputError` return 502.
- Regeneration safety: old drafts are archived **only after** successful AI generation — if generation fails, the old draft is preserved intact.
- Provider exception hierarchy: `AIProviderError` base, `UnknownAIProviderError`, `AIProviderGenerationError`, `InvalidAIProviderOutputError`.

### Phase 8E — Cockpit Opportunity AI Workflow UX

- Added AI-assisted draft actions section to the Cockpit `OpportunityShow` component:
  - **AI Draft Preview**: opens a read-only dialog showing generated subject, body, safety note, and provider metadata.
  - **Generate AI Draft**: creates a new AI draft with duplicate prevention (returns existing active AI draft if one already exists).
  - **Regenerate AI Draft**: archives old drafts after successful regeneration.
- Displayed informational bullet points explaining the workflow (preview is read-only, duplicate prevention, safety-first regeneration, mandatory human validation).

### Phase 8F — MessageDraft Human Review UX

- Added `WorkflowPanel` component to `MessageDraftShow` showing current status chip and grouped action buttons:
  - **Review Submission** (draft/rejected → needs_review)
  - **Human Decision** (needs_review → approved or rejected)
  - **Sending** (approved → sent_manually)
  - **Maintenance** (archive)
- All actions use confirmation dialogs with optional `review_notes` input.
- "Mark Sent Manually" includes a warning that it does **not** send an actual email.
- Added `AiAuditCard` component that displays AI metadata fields (Generated By, AI Provider, Model Name, Prompt Profile, Prompt Version) when present.
- Added `MessageContentCard` for read-only subject/body display.

### Provider Registry

Providers are registered via the `@register_provider(name)` decorator and resolved via `get_ai_provider()`. The registry is a module-level `dict[str, type]`.

Current registered providers:
- `mock_ai` — `MockAIProvider` (deterministic, French prospecting email generation)

```
AIProviderError (base)
├── UnknownAIProviderError    — unknown provider name (raised during resolution)
├── AIProviderGenerationError — runtime failure during generation
└── InvalidAIProviderOutputError — output missing required keys or invalid values
```

## Human Validation Rules

1. **Preview creates nothing** — `GET /ai-draft-preview` is read-only. It builds the prompt, calls the provider, and returns the result. No MessageDraft, no ComplianceEvent, no opportunity status change.

2. **Generate creates draft only** — `POST /generate-ai-draft` creates a MessageDraft with `generated_by="ai"` and creates a `message_generated` ComplianceEvent. The draft starts in `draft` status. Duplicate prevention returns the existing active AI draft if one already exists.

3. **Approve is human validation** — `POST /message-drafts/{id}/approve` transitions the draft from `needs_review` to `approved`. This is the explicit human validation gate. The endpoint sets `approved_at` and creates a `message_approved` ComplianceEvent.

4. **Mark-sent-manually records external sending but does not send email** — `POST /message-drafts/{id}/mark-sent-manually` transitions from `approved` to `sent_manually`. It records `sent_at`, creates a `message_sent` ComplianceEvent, and schedules a 7-day follow-up. **No email is actually sent by the platform.**

5. **No automated external message sending** — The platform never sends messages to external systems automatically. Every external communication requires explicit human action.

### Status Lifecycle

```
draft ──(submit-review)──> needs_review ──(approve)──> approved ──(mark-sent-manually)──> sent_manually
                                              └──(reject)──> rejected ──(submit-review)──> needs_review
```

### Opportunity Status Sync

```
draft ──> draft_ready
needs_review ──> waiting_validation
approved ──> approved
rejected ──> draft_needed
sent_manually ──> follow_up_needed
```

## Audit Metadata

The `MessageDraft` model stores the following audit fields:

| Field | Type | Description |
|-------|------|-------------|
| `generated_by` | `str` | Origin: `"system"`, `"manual"`, `"rule_based"`, or `"ai"` |
| `ai_provider` | `Optional[str]` | Provider name (e.g. `"mock_ai"`) |
| `model_name` | `Optional[str]` | Model name (e.g. `"mock-soria-v1"`) |
| `prompt_profile` | `Optional[str]` | Prompt profile identifier (e.g. `"prospecting_fr_v1"`) |
| `prompt_version` | `Optional[str]` | Prompt version (e.g. `"ai-draft-v1"`) |
| `review_notes` | `Optional[str]` | Human review notes from submit-review, approve, or reject |
| `approved_at` | `Optional[datetime]` | Timestamp of human approval |
| `sent_at` | `Optional[datetime]` | Timestamp of manual send recording |

### Compliance Events

| Event Type | Triggered By | Description |
|------------|-------------|-------------|
| `message_generated` | `generate-ai-draft`, `regenerate-ai-draft` | Draft created by AI |
| `message_approved` | `approve` | Draft approved by human |
| `message_sent` | `mark-sent-manually` | Draft recorded as sent |

## Safe Failure Behavior

1. **Diagnostics endpoint** — `GET /opportunities/ai-diagnostics/provider` is fully read-only. It reports the configured provider, model, prompt profile/version, lists all available providers, and indicates whether the configured provider is resolvable. No database mutations.

2. **Unknown provider returns controlled failure** — If `AI_DRAFT_PROVIDER` is set to an unknown value, `generate_ai_draft()` raises `UnknownAIProviderError`, which the endpoint converts to HTTP 503 with a descriptive message.

3. **Regenerate generates first, archives old drafts only after success** — The `regenerate-ai-draft` endpoint calls `generate_ai_draft()` **before** archiving any existing drafts. If generation fails (exception from provider or invalid output), the old draft remains active and unchanged. Archival only proceeds after successful generation.

4. **Output validation** — `_validate_ai_result()` checks that the provider output contains all required keys (`subject`, `body`, `provider`, `model_name`, `prompt_version`, `safety_note`) and that the non-empty keys have non-empty string values. Invalid output raises `InvalidAIProviderOutputError` → HTTP 502.

5. **No partial mutations** — The orchestrator (`generate_ai_draft()`) produces a validated result dict. The endpoint is responsible for database writes within a single transaction. If the endpoint fails mid-write, the database transaction rolls back.

## Current Limitations

1. **Provider is deterministic `mock_ai`** — `MockAIProvider` generates the same output for the same context every time. It is not connected to any external AI API.

2. **No OpenAI/Claude API integration yet** — The provider abstraction is designed to support real AI providers (OpenAI, Claude, etc.), but none have been implemented.

3. **No France Travail API yet** — Importing opportunities from France Travail is planned for a future phase.

4. **No automatic email sending** — The platform records manual sends but does not integrate with any email sending provider (SMTP, SendGrid, etc.).
